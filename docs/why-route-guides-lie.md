# 为什么 AI 写的骑行路书不可信，以及怎么治

> 一个用多 agent + 证据门禁给路书做核验的开源项目，以及它背后的几个设计取舍。

---

## 一、骑友真正的痛点不是"没有路书"

随便打开一个骑行 App，路书多得看不完。问题是**没有一份能被信任**。

我见过太多这样的句子：

> "全程平路，休闲骑，适合新手。"

骑完发现累计爬升 900 米，六小时才到。

> "K42 有便利店，可以补水。"

到那儿发现店三个月前就关门了。

> "风景绝美，值得一去。"

这句倒是真的——但它不可核验，也不该被当成事实来读。

前两类是**可以被验证的断言**，只是没人验证。第三类是**主观描述**，本来就不该进核验范围。

而 AI 生成的路书把这三类混在一起，还统一用一种自信的语气写出来。它会把空白补成"沿途风景优美、补给充足、路面平整"——因为它不知道，而它的训练目标是"写出一段通顺的话"，不是"说真话"。

**这就是问题：让 AI 写路书，会让原有的问题更严重。**

---

## 二、一个简单但少有人做的决定：路书是待核验对象，不是证据

大多数"AI + 文档"的系统走的是 RAG 路线：把文档切块、检索、让模型基于检索结果回答。

这个思路用在路书上会失效。因为路书本身就是要被检验的东西。**拿路书去证明路书，是自我循环。**

所以这个项目的第一条硬约束是：

> 路书里的每一句话，必须和**独立于路书**的证据对上。路书自己不算证据。

独立证据包括：

- GPX 轨迹（真实走过的路）
- DEM 高程（判断坡度）
- OSM 路网与 POI（判断路面、补给、隧道）
- 气象数据（判断季节风险）

---

## 三、把"一段话"拆成"几条断言"

这是整个系统最基础也最容易被低估的一步。

原句："坡度平缓，适合新手，沿途有便利店。"

拆成：

| 断言 | 类型 | 可核验性 |
|---|---|---|
| 坡度平缓 | slope | 高（有 DEM/GPX 就能算） |
| 适合新手 | 主观 | 不可核验 |
| 沿途有便利店 | supply | 中（OSM POI，容易过时） |

为什么要拆？因为**段落级的引用会掩盖"一段里三句真一句假"**。只有原子化之后，才能逐条判、逐条给出处。

项目里定义了六类可核验断言（坡度、路面、交通、补给、遮荫、可通行）和一类明确不可核验的（风景/主观）。最后这一类很重要——**不是所有断言都该被核验**，把主观描述标成"主观"而不是"未核实"，是避免"过度保守"的关键设计。

## 四、三态裁决 + 一个不肯妥协的地方

每条断言最终落在四种状态之一：

| 状态 | 含义 |
|---|---|
| `supported` | 证据支持 |
| `contradicted` | 证据与断言矛盾 |
| `unverified` | 找不到可用证据 |
| `subject` | 主观描述，不参与核验 |

看起来平平无奇。真正麻烦的是**证据不完整**的时候。

举个真实踩过的坑：

第一次跑核验时，某条"沿途有便利店"被判成了 `contradicted`——因为 OSM 在这个区域查不到便利店。

但那次是**网络超时**，请求根本没发出去。程序把"没拿到数据"当成了"数据说没有"。

这是一个非常典型的错误，而且它会**把真话判成假话**——比漏判严重得多。

修法是把两种情况分开：

```python
# 不是"查到了空"，而是"根本没查"
if not context.available:
    return unverified      # 未核实，不是矛盾

# 查到了，但该区域 POI 少于 3 个
if context.poi_sparse:
    return unverified      # 数据太稀疏，不足以否定
```

同样的坑还有第二个：POI 覆盖稀疏的山区，OSM 上什么都没有。如果按"没查到 = 没有"处理，所有山区路书都会被判成满篇谎言。

**"未知" 不等于 "否定"** —— 这条规则现在写进了项目的安全默认值：

```python
SAFE_DEFAULT_RISK = 2   # 证据不足时，风险默认按较高值处理
```

宁可保守，不可冒进。

## 五、多 agent 不是为了炫技，是为了让分歧留在台面上

系统里有三个角色：

1. **生产者**：从各个证据源取数据，给出自己的判断和置信度
2. **溯源者**：专门找反证——它的任务是反驳，不是确认
3. **仲裁者**：综合两边，按证据质量与时效加权

为什么要有"专门找反证"的角色？因为单个模型倾向于**确认已有结论**。让它同时做"支持"和"反对"两件事，它会偏向自己先写下的那个。

分开之后，分歧会被显式记录下来。当两个证据源真的冲突（OSM 说是铺装路，轨迹显示是砂石路），系统不会强行给一个结论，而是**并列展示两方证据，交给人判断**。

这是刻意的：宁可让你看到矛盾，也不要系统替你猜。

## 六、诚实的代价

这套设计有个明显的副作用：**"未核实"会很多**。

一份 10 条断言的路书，可能有 4 条标着"未核实"。用户第一反应是"这工具什么都不知道"。

这正是项目里最值得研究的问题：**把不确定性作为一等输出，代价有多大？**

可能的答案是：存在一个最优点——未核实率太低说明系统在瞎猜，太高说明它没用。找到这个点，需要用户实验。

但有一点我比较确定：**用户宁愿看到"这条我没核实"，也不愿看到一句编得很顺的假话。** 前者只是不方便，后者会让人在山里没水喝。

## 七、工程上踩过的几个坑

写代码的过程里，有几个错误值得单独记下来，因为它们都属于"看起来很对、实际很坏"：

**1. 合成数据冒充真实数据源**

演示用的环境指标本来是随机生成的，但证据来源写成了 `sentinel-2:L2A`。报告里看起来就像真实卫星反演。

这违背了项目自己的立身之本——**出处本身不能是假的**。现在统一标 `synthetic:v1`，目标数据源写进备注。

**2. 缓存键没带引擎签名**

换了路线引擎，缓存还在复用旧结果，导致同一个"1708 公里"的错误反复出现。用户以为改了配置，其实什么都没变。

**3. 静默降级**

路由服务不可用时，程序悄悄退回直线，生成一个只有 4 个点的 GPX。用户拖进码表以为能用，其实是一条直线。

现在的规则是：**拿不到真实路网就报错，不产出假路线**。直线模式的产物必须叫 `route_直线近似_不可导航.gpx`。

这三个 bug 有共同点：**它们都不会让程序崩溃，只会让用户拿到错的东西而不知道。**

---

## 八、这个项目现在是什么

一句话：**给骑行路书做事实核验，并用真实路网生成行程。**

技术上：

- 纯 Python 标准库，零依赖
- 41 条测试，CI 覆盖 Python 3.10–3.12
- 证据层：OSM / DEM / 气象，全部免费无需 key
- 路由：BRouter（带高程）→ OSRM → 严格报错
- 住宿：Photon（免费）→ Overpass 兜底
- 界面：本地网页版，一句话进，行程 + GPX 出

它不完美。自动生成的路线仍然比真实骑行里程长 1.7 倍（OSM 中国数据缺自行车通行标记），"沿海骑行"这类偏好还没真正约束路线，乡镇级住宿经常查不到。

但它在**该说不确定的时候说"不确定"**——这一点，我觉得比多给几个功能重要。
